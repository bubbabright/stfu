# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

STFU — a Windows-only HTPC volume control + closed-caption tool. Runs on a Windows 11 media PC ("pluto"), exposes volume control via a REST web UI, an on-screen overlay, MQTT pub/sub for edge devices (phone/tablet/ESP32), and an MCP server for AI-driven control. No test suite or lint config currently exists in the repo despite references to them in README.md — verify before relying on `pytest`/`ruff`/`black` commands.

## Deployment

Live instance runs on `pluto` (Windows 11 HTPC). Reach it with `ssh pluto`. `C:\scripts\stfu` on pluto is a **separate git clone** of this same repo (github.com/bubbabright/stfu) — not shared NAS storage. Editing files here does NOT change what pluto sees; deploy by committing here, `git push`, then `ssh pluto` and `git pull` (check `git status`/`git diff` there first — pluto's working tree can carry its own uncommitted edits). After pulling, the running processes still need restarting manually — see below.

**No autostart, on purpose.** Scheduled Tasks were tried and dropped (2026-08-29/30) — pluto runs for weeks between reboots, so autostart-on-boot reliability wasn't worth what it cost. The original writeup of that cost cited two symptoms: `Stop-ScheduledTask` silently leaving the old python.exe process tree alive, and one night every one of the three module tasks turning up "double-running" (2 live processes each). **Correction (2026-09-03): the double-running symptom was a false alarm, not a Scheduled-Task bug** — see below, it's normal Windows venv behavior present under manual `manage.bat` launch too, so it shouldn't have counted as evidence against Scheduled Tasks. The decision to stay manual stands anyway (pluto reboots rarely enough that autostart-on-boot reliability isn't worth much regardless), but if autostart is ever reconsidered, the only real open question is the `Stop-ScheduledTask` orphaning — task/trigger/action definitions were each verified singular at the time, no Startup-folder or Run-key culprit found, cause still not conclusively identified. All three tasks were deleted; Daniel starts STFU by hand each session via `manage.bat`.

**"2 processes per module" is normal, expected, Windows-only — not a bug.** Every `manage.bat`-launched module shows up as **two** `python.exe` PIDs in `Get-CimInstance Win32_Process`, both with the identical `-m stfu ...` command line: `.venv\Scripts\python.exe` (parent) and `C:\Program Files\Python314\python.exe` (child, `ParentProcessId` = the venv one). Verified this is CPython's own official venv launcher redirector, not a uv-specific stub or a custom bug: `(Get-Item .venv\Scripts\python.exe).VersionInfo` reports `InternalName: Python Launcher`, `OriginalFilename: py.exe`, `CompanyName: Python Software Foundation`, and file sizes/`LinkType` confirm the two `python.exe`s are distinct real files, not a symlink to the same one. **Root cause: Win32 has no in-place `exec()`** — `CreateProcess` always creates a new process object — so CPython's venv redirector (`PC/venvlauncher.c`; shipped since 3.7.2, docs.python.org/3/library/venv.html "Changed in 3.7.2/3.7.3"; renamed `venvlauncher.exe`/`venvwlauncher.exe` in 3.13+) has no choice but to spawn the real base-install interpreter as a child rather than replace itself. It finds `pyvenv.cfg`, resolves the base interpreter, sets `__PYVENV_LAUNCHER__` to its own path, `CreateProcess`'s the real interpreter with the original argv, and waits — under a **job object**, so killing the redirector should take the child down with it (which is exactly why the Scheduled Task orphaning above doesn't fit "normal clean kill" — it points at `Stop-ScheduledTask` itself, not at this redirector mechanism). The real interpreter reads `__PYVENV_LAUNCHER__` into `sys._base_executable`; `sys.executable` still reports the redirector's own path — code that needs the real base interpreter path should read `sys._base_executable`, not `sys.executable`. This is **structurally impossible on Linux**: confirmed empirically that both stdlib `python3 -m venv` and `uv venv` on Debian 13 produce `bin/python` as a real symlink straight to the interpreter binary, so `execve()` replaces the process image in place — always exactly 1 PID, no parent/child split, ever. **How to apply:** don't treat 2 PIDs per module as a stuck/duplicate process — check `ParentProcessId` before assuming a bug. A liveness/status check should key off the parent (`.venv\Scripts\python.exe`) PID, not assume one PID = one module instance.

**Modularity is a deliberate, valued property of this app — not incidental, don't collapse it.** Web/overlay/night-light-helper stay three separately-launchable processes even though nothing forces that anymore now that everything runs from the interactive session by hand (the old SYSTEM-vs-interactive-session split that originally forced the night-light helper into its own process is gone, but the module boundary itself should stay). Reason: this app is still under active development on two fronts that need the pieces to stay independently swappable —
- **REST → MQTT migration in progress.** Volume/nightlight control currently goes over REST (`web.py`); the plan is to run REST and MQTT in parallel during the transition, then likely retire REST once MQTT covers everything. `mqtt.topic_volume_state`/`topic_volume_set` already exist in `config.py` but nothing subscribes to them yet — that's this migration's landing spot, not dead code to clean up.
- **Linux port planned.** The app is Windows-only today (pycaw/comtypes/tkinter/`winreg`), but cross-platform support is on the roadmap.

Keep new functionality along these same lines — a new capability gets its own mode/flag rather than being folded into an existing one, unless there's a concrete reason to share a process. Prefer designs that let a piece (e.g. the transport, or a platform-specific controller) be swapped or pulled out wholesale rather than threaded through everything else.

## Commands

```bat
setup.bat   # uv venv + install deps (no task registration — see Deployment)
manage.bat  # menu: start/stop each module by hand, or all of them, or check status

python -m stfu                       # web + overlay + captions in one process (dev/manual use only)
python -m stfu --no-overlay          # the "web" module
python -m stfu --overlay-only        # the "overlay" module
python -m stfu --night-light-helper  # the "nightlight" module — interactive session only
python -m stfu --tint-only           # the "tint" module — interactive session only
python -m stfu --mcp                 # MCP server (stdio, on-demand)
python -m stfu --config path.toml    # override config file path
```

The app is Windows-only (pycaw/comtypes for audio, tkinter overlay) — it will not run on Linux/macOS. There is no test or lint tooling pinned in `requirements.txt`. The Python environment is managed by `uv` — one canonical `.venv`, not a per-tool venv sprawl.

## Architecture

Single entry point, one run mode per module (see the Deployment table), all sharing the same `AppConfig`:

- `stfu/__main__.py` — argparse dispatch. Bare `python -m stfu` (no flags) starts Flask, overlay, and captions all in one process on daemon threads, then busy-waits (`sleep(1)` loop) until `KeyboardInterrupt` — convenient for local dev/manual testing, not how it's deployed. `--mcp`, `--night-light-helper`, `--overlay-only`, and `--tint-only` each bypass that and hand off entirely to their own function (`mcp_server.create_mcp_server`, `night_light_helper.run_night_light_helper`, `overlay.run_overlay`, `tint.run_tint`) — these are the actual production modules, each started by hand via `manage.bat` (see Deployment — modularity here is intentional, don't merge these). There is no `--service` mode — no `service.py` exists in this repo; ignore any doc that says otherwise.
- `stfu/config.py` — one `@dataclass` per `stfu.toml` section (`VolumeConfig`, `WebConfig`, `OverlayConfig`, `MQTTConfig`, `CCConfig`, `NightLightConfig`, `TintConfig`, `MCPConfig`, `LogConfig`), composed into `AppConfig`. Each dataclass self-validates in `__post_init__` (range/positivity checks) and raises `ValueError` on bad values — config errors are fail-fast at startup, not silently clamped. `load_config()` reads TOML, deep-merges it over the dataclass defaults section-by-section, and warns (not errors) on unknown TOML keys via `VALID_KEYS`. `MQTTConfig.broker` defaults from the `MQTT_BROKER` env var, everything else only from TOML/defaults. `NightLightConfig.helper_port`/`helper_timeout` (default `5100`/`2.0`) configure `night_light_helper.py`'s own listen port.
- `stfu/audio.py` — `AudioController` wraps pycaw. COM is initialized and the `EndpointVolume` interface is cached once in `__init__` (not per-call — this was a real perf fix, see README changelog), guarded by a `threading.Lock` since it's shared across the Flask thread, overlay thread, and MCP tool calls.
- `stfu/web.py` — `create_app(audio, config, nightlight=None, tint=None)` factory returns `(Flask app, cc_queue)`. All routes read/mutate state through the injected controllers, no module-level globals. `/cc/stream` (SSE) exists but is currently unused — captions ship over MQTT instead, not this endpoint. `/nightlight` and `/tint` + `/tint/opacity` each relay to their interactive-session helper process via HTTP client and return `503` if it's unreachable — never a silent no-op. `/mcp/status` reports MCP liveness for the web UI's status light by checking the mtime of the heartbeat file `stfu.mcp_server.heartbeat_path()` writes (see below) — 404s if `config.mcp.enabled` is `False`, which is the default.
- `stfu/mcp_server.py` — `create_mcp_server(audio, config=...)` factory using FastMCP, same dependency-injection pattern as `web.py`. Exposes `get_volume`/`set_volume`/`volume_up`/`volume_down`/`toggle_mute`/`set_mute`. `heartbeat_path(config)`/`start_heartbeat(config)` let the `--mcp` process (`__main__.py`) touch a file on a timer for as long as it's alive — `web.py`'s `/mcp/status` reads that file's mtime rather than polling a port, since MCP runs over stdio (spawned on-demand by the MCP client, no listening port to check). `config.mcp.enabled` defaults to `False` — MCP is fixed and functional but parked off by default; flip it on in `stfu.toml` to use it again.
- `stfu/nightlight.py` — the Windows **Night Light** blue-light filter. Its registry state is an undocumented, version-fragile binary blob, so this shells out to an off-the-shelf CLI (`wnl`, path in `config.nightlight.wnl_path`) instead of hand-patching it. `NightLightController` runs `wnl status|on|off` via `subprocess` and parses stdout — it never touches `winreg` itself, `wnl.exe` does internally. `HTTPNightlightClient` talks to `night_light_helper.py` over `config.nightlight.helper_port`/`helper_timeout` (see next entry).
- `stfu/night_light_helper.py` — `run_night_light_helper(config)`, dispatched via `--night-light-helper`. The **only** place `NightLightController` is ever constructed — `wnl.exe` needs `HKEY_CURRENT_USER`, scoped to the caller's logon session. Every other run mode reaches it over HTTP through `HTTPNightlightClient`. Same underlying constraint the tkinter overlay already works around (a headless/SYSTEM process can't touch the interactive desktop either) — a separate interactive-session process, reached over HTTP instead of touched directly.
- `stfu/overlay.py` — tkinter on-screen volume display, polls `AudioController` on a timer. `run_overlay()` creates a fresh `Tk()` each call — only one overlay can run per process (known limitation, not currently guarded). Dispatched via `--overlay-only` — its own process, not bundled into the web module, since it needs the interactive session the same way the night-light helper does. Click-through/transparency here is `-transparentcolor "black"` (colorkey — black pixels become invisible).
- `stfu/tint.py` — fullscreen click-through black veil for a "night light on steroids" sleep-tint effect, adjustable opacity via a web UI slider (`/tint`, `/tint/opacity`). Dispatched via `--tint-only`, its own process — same interactive-session constraint as `overlay.py`, but **can't reuse `overlay.py`'s transparency technique**: black is already `overlay.py`'s magic transparent-color key, so a solid-black tint window would render invisible under that trick instead of opaque. Uses the other Windows mechanism instead: `WS_EX_LAYERED|WS_EX_TRANSPARENT` (real click-through) + Tk's own `-alpha` (opacity) via `ctypes`. Runs its own tiny Flask control server (`config.tint.control_port`, default `5103`) on a daemon thread, same `_run_status_server`-alongside-`Tk()` pattern as `overlay.py`; mutating the Tk window from that server's request thread goes through `root.after(0, ...)` since tkinter isn't thread-safe. `HTTPTintClient` (same file) is what `web.py`/`__main__.py` actually talk to. Primary display only — no multi-monitor support (same limitation as `overlay.py`).
- `stfu/captions.py` — `CaptionCapture` grabs screen frames with `mss`, OCRs with Tesseract, publishes to MQTT (`htpc/captions`). Key design point: it checks MQTT subscriber presence before running Tesseract, so OCR only burns CPU when something is actually listening for captions. Reconnects to the broker with exponential backoff (1s→30s, jittered) and has a `_stop_event`/`stop()` for clean shutdown. Currently started as a thread inside whichever process has `cc.enabled = true` (off by default) — note this thread would need the same session-scoped treatment as overlay/night-light if ever run inside the `STFU_Web` (SYSTEM) module, since `mss` also needs desktop access; not yet split into its own module since it's dormant.

State flows one way through MQTT: `pycaw` (this app) is the source of truth for volume, publishing to `htpc/volume/state`; edge devices (browsers via MQTT-over-WebSocket, ESP32 nodes) publish commands to `htpc/volume/set` which this app subscribes to. Caption text flows `mss`/Tesseract → `htpc/captions` → tkinter overlay + browsers.

`archive/` is legacy pre-rewrite code (gitignored) — not part of the active package, don't treat it as current architecture reference.
